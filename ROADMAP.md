# Roadmap

Tracked improvements, fixes, and open questions per package. Findings are grouped by category. Severity is indicated where relevant.

---

## MartinDrozdik.DDD

Core DDD primitives. Reviewed (including `Mediator`).

### Bugs

- [x] **`IntIdentity` / `StringIdentity` are unusable as documented** — both declared `where TSelf : ..., new()` (`Identities/Primitive/IntIdentity.cs:5`, `StringIdentity.cs:5`), unlike `GuidIdentity`. A derived type with a primary constructor (e.g. `OrderId(int key) : IntIdentity<OrderId>(key)`, as shown in the skill docs) has no parameterless constructor and **failed the `new()` constraint → CS0310, won't compile**. Only `GuidIdentity` was exercised, so it went unnoticed. **Fixed:** dropped `, new()` from both; added `Identities/Primitive/PrimitiveIdentityTests.cs` whose derived types act as a compile-time regression guard.
- [x] **Broken interpolation in duplicate-detection message** — `Enumerations/Statics/ThrowIfDuplicates.cs:32-33` interpolates an unmaterialized `IEnumerable<(T,int)>`, so the exception prints the iterator type name instead of the duplicates. Fix: report `duplicates.Count` and the offending names.
- [ ] **Wrong variable in `UrlBuilder` port error** — `Integrations/UrlBuilder.cs:120` interpolates `port` (still `null` after a failed parse) instead of `portPart`; message reads "Port  could not be parsed".

### Design

- [ ] **`Error` includes `Exception` in value-equality** (`Errors/Error.cs:97`) — `Exception` uses reference equality + reference-based hash, breaking the `ValueObject` value-semantics contract (dictionary/set behavior, hash stability). Exclude it from `GetEqualityComponents()` (compare on `Code` + `Message` + `Details`), consistent with `ErrorBuilder.WithSubErrors` already ignoring exceptions.
- [ ] **`EnumerationName` validation hole** (`Enumerations/EnumerationName.cs`) — it's a `struct` with `init` setters, so `default(EnumerationName)` and object-initializer usage bypass the validating constructor → `Key == null` despite the "must not be empty" contract.
- [ ] **`EnumerationName.KeyLowercase` is dead state** — computed/stored per instance "for case-insensitive comparisons," but the type doc says "Case sensitive" and `Equals`/`GetHashCode` only use `Key`. Never read. Remove it or actually honor it.
- [ ] **Inconsistent generic-parameter ordering across services** — `IGetByIdService<TItem, TIdentity>` (item-first) vs `ISaveService<TIdentity, TItem>` (identity-first) vs `ICrudService<TEntity, TIdentity>`; `ICrudService` flips order when composing. Pick one convention. Also `IGetByIdService` is missing `where TIdentity : notnull`.
- [ ] **Enumeration static cache: thread-safety & encapsulation** — `StaticEnumeration<TSelf>.EnsureInitialized()` / `InitializableEnumeration` do non-locked check-then-init over mutable statics (double-init / partial-dictionary race). `EnumerationsDictionary`/`EnumerationsList` are `protected internal { get; set; }` (publicly reassignable). Consider `Lazy<T>`/lock and `private` setters.
- [ ] **`ValueObject` is its own `IEqualityComparer<ValueObject>` and lacks `IEquatable<ValueObject>`** (`Templates/ValueObject.cs:14`) — unusual responsibility mix; `IEquatable<ValueObject>` is the conventional, allocation-friendly choice. Reconsider.
- [ ] **`ValueObject`/`Enumeration` equality is untranslatable in EF Core queries** — `Templates/ValueObject.cs` overloads `operator ==`, so a predicate over a value-converted property compiles to a static method call rather than an equality node and EF Core cannot translate it. `context.Invoices.Where(i => i.State == InvoiceState.Draft)` — the obvious way to filter on an `Enumeration` mapped with `HasConversion` (`Demo/Context/Configurations/InvoiceConfiguration.cs:55-60`) — throws "could not be translated" at runtime, verified while writing the Demo recurring task. Since `Enumeration : ValueObject` this hits every enumeration-typed column, i.e. the single most likely thing to appear in a `Where`. Either document the working alternative or give `Enumeration` an EF-friendly comparison path.
- [ ] **Generic CRUD services vs. DDD** — `Services/ICrudService` & friends are a generic repository/CRUD abstraction, which sits in tension with rich aggregate modeling. Keep as pragmatic convenience, but add a doc note clarifying it's not the recommended way to model rich aggregates.
- [x] **Struct-enum interop: finish outside the core package** — the core half shipped (`Enumerations/EnumerationStructExtensions.cs`, `EnumerationNameAttribute`, `Statics/StructEnumNames.cs` + `StructEnumMap.cs`, `Validations/*`, `FromStructEnum` on both bases). Blocked on publishing core 0.8.0, because `.Web`/`.Testing`/Demo compile against the *published* core. Then: (1) ship `EnumerationAssert.MapsToStructEnum<TEnumeration, TEnum>()` in `.Testing` — now only a thin xUnit wrapper over the core `EnumerationStructMapping.ThrowIfIncomplete<TEnumeration, TEnum>()`, which already asserts the two member sets are a bijection; it should catch the `ArgumentException` and re-report it through `Assert.Fail` so the failure reads as an assertion rather than an argument error; (2) convert Demo `InvoiceState` to `StaticEnumeration<InvoiceState>` — its members are static *properties*, invisible to `GetAllStaticMembers`, they must become `public static readonly` fields, and `InvoiceConfiguration.cs:55-60` should then convert via `InvoiceState.FromName(e).Value`; (3) add `InvoiceStateDto` and replace `State = i.State.ToString()` in `GetInvoicesQueryHandler.cs:18`. **Trap:** `ToStructEnum` is not EF-translatable, so that projection must materialise before mapping. **Fixed:** all three shipped. `.Testing` gained `Enumerations/EnumerationStructMappingTests.cs` — a single generic base class `EnumerationStructMappingTests<TEnumeration, TEnum>` whose five inherited facts cover the bijection, both per-member conversions and both round trips, so a consumer writes one empty class declaration per mapping. `.Testing` now references `MartinDrozdik.DDD.Web` 0.8.1 (which brings core 0.8.1). Demo `InvoiceState` is a `StaticEnumeration<InvoiceState>` with `public static readonly` fields and a private constructor, `InvoiceConfiguration` converts via `FromName(e).Value`, and `GetInvoicesQueryHandler` materialises before `ToStructEnum<InvoiceStateApi>()`. `InvoiceStateApi` carries `[JsonConverter(typeof(JsonStringEnumConverter<InvoiceStateApi>))]`, so the wire format stays `"state": "Draft"` and Kiota now generates a client-side enum. Demonstrated by `Demo.Tests/Invoices/InvoiceStateMappingTests.cs`.
- [ ] **Struct-enum mapping is verified only when someone remembers to ask** — `EnumerationStructMapping.ThrowIfIncomplete<TEnumeration, TEnum>()` (`Enumerations/EnumerationStructMapping.cs`) is opt-in, so an app that never calls it still discovers a broken mapping as a runtime `BusinessRuleException`. `AddAppServices()` in `.Web` could take the pairs to verify and run them at startup, turning the guard into something you configure once rather than a call each app has to remember. Blocked on the same publish round-trip as the item above.
- [ ] **Revisit `Result<T, E>` / `UnitResult<E>` as C# 15 union types** — tracked by `TODO` comments in `Results/Result{T,E}.cs` and `Results/UnitResult{E}.cs`. Union types ship with C# 15 / .NET 11 (GA expected November 2026) and would give compiler-verified exhaustive matching and retire the hand-written success/failure guards. The blocker is storage: a *declared* union compiles to a struct whose only field is an object reference, so every success would box the value and every failure the error — a regression for types on hot paths. The route worth taking is the *custom* union (keep the current layout, mark it with the `Union` attribute from `System.Runtime.CompilerServices`, expose one case type per state), which was not usable yet in .NET 11 Preview 2/3 because union member providers and the runtime polyfills had not shipped. Re-evaluate at .NET 11 GA and adopt only if the allocation profile stays flat.
- [ ] **`MartinDrozdik.DDD.Results` shadows ASP.NET Core's `Results` helper** — inside any namespace nested under `MartinDrozdik.DDD`, the bare name `Results` now binds to this namespace, so `Results.Problem(...)` no longer compiles. Fixed in-repo by moving `.Web`, `.Testing` and `.Web.Tests` to `TypedResults` (the recommended API anyway), and consumers with their own root namespace are unaffected. The `ddd-web` skill now carries an **Endpoint results: `TypedResults`, never `Results`** section and the `ddd` skill cross-references it, so generated code avoids the trap; a line in the `.Web` README would still help anyone reading only that.
- [ ] **`FromStructEnum` throws while `FromName` returns a result** — deliberate (an unmapped member is a broken mapping contract, i.e. a bug, not a business failure) and documented on both methods, but the asymmetry between two sibling static factories on the same base is worth revisiting if it trips anyone up.

### Dependency issues

- [x] **`CSharpFunctionalExtensions` leaks through the public API** — `Result<T>` / `IResult<T,Error>` / `UnitResult<Error>` appear in public signatures (`IGetByIdService.GetAsync`, `StaticEnumeration.FromName`, `ErrorBuilder.BuildUnitResult`, …) and are advertised in the README/`CLAUDE.md` as if first-class library types. Either own the abstraction (thin wrapper / explicit re-export) or document clearly that `Result<T>` *is* CSharpFunctionalExtensions, since consumers inherit a hard third-party dependency and its versioning. **Fixed:** the abstraction is owned. `Results/` in the core package now holds `Result<T, E>`, `UnitResult<E>`, the `IResult`/`IValue<T>`/`IError<E>`/`IUnitResult<E>`/`IResult<T, E>` interfaces, `ResultFailureException`/`ResultSuccessException`, and `ResultExtensions`/`AsyncResultExtensions` (`Map`, `MapError`, `Bind`, `Ensure`, `Tap`, `TapError`, `Match` + `Async` counterparts). Both result types are `readonly struct`s with the same shape as the package they replace, so every call site changed only its `using`. The `CSharpFunctionalExtensions` `PackageReference` is gone from `MartinDrozdik.DDD.csproj`, which also drops it from `.Options`, `.Web` and `.Testing` transitively. Covered by `Tests/Results/{Result,UnitResult,ResultExtensions,AsyncResultExtensions}Tests.cs`.

### NuGet split

- [ ] **Non-DDD utilities dilute the core package** — `Extensions/{String,Random,CurrencyFormat,Url,Path}Extensions`, `Integrations/UrlBuilder`, `Disposing/DisposableAction` have nothing to do with DDD. Most egregious: **`CurrencyFormatExtensions.ToCzk()`** hardcodes Czech koruna (`"Kč"`) — application-specific logic in a general library. Consider extracting to a separate `MartinDrozdik.Common`/`.Utilities` package; at minimum drop `ToCzk`.

### Minor

- [ ] **Doc/naming drift** — `CLAUDE.md` says `ValidationException` but the type is `BusinessRuleValidationException`. `StringExtensions` & `CurrencyFormatExtensions` both have the XML summary "Extensions for currency formatting." (copy-paste). `EnumerationErrors.EnumerationNameNotFound` passes `name` twice to `string.Format` — verify the resx uses `{0}`/`{1}`. **Partially fixed:** the `string.Format` bug is gone — resx files were removed library-wide (localization is not wanted, it made error messages culture-dependent) and the message is now an interpolated English string using `name` and `enumName`.
- [x] **`Enumerations/Statics` namespace does not match its folder** — every file there declares `namespace MartinDrozdik.DDD.Models.Enumerations.Statics` (note the stray `Models.`) while the folder is `Enumerations/Statics`. A legacy leftover; new files in the folder follow it for consistency, so the rename should be done in one go.
- [ ] **`ToUrlFriendlyFileName` no-extension branch** (`Extensions/UrlExtensions.cs:36-38`) — missing the `.Trim('-')` the other branches apply, and the outer `Substring(0, maxLength)` is redundant since `ToUrlFriendly` already enforced `maxLength`.
- [ ] **`SpecificationResult.NotSatisfied(IEnumerable<Error>)` contract mismatch** — throws on empty, while the private ctor silently normalizes empty → satisfied. Harmless but inconsistent.
- [ ] **`IdentityConverter` only provides `CreateGuid`** — no `CreateInt`/`CreateString` factory counterpart (mirrors the `GuidIdentity`-only reality above).

### Notes (keep doing)

- Specifications module is excellent: clean composition, deferred allocations (`errors ??= []`), correct AND/OR short-circuit semantics.
- `Results/` mirrors the Specifications module's discipline: `readonly struct`s with no heap traffic, guards that fail fast on a failure without an error, and composition helpers that all short-circuit the same way.
- `ErrorBuilder` fluent API with fail-fast guards; correct, bounds-safe span/stackalloc usage; immutable `record` `UrlBuilder` with invariant checks; consistent file-scoped namespaces, thorough XML docs, `DebuggerDisplay`.

### Mediator

CQRS mediator (`Mediator/`): marker interfaces (`IMessage`/`IRequest`/`ICommand`/`IQuery`), `ServiceMediator`, DI registration (`AddMediator` → `ServiceMediatorConfig`), composable pipeline behaviors, and the `IServicePipelineIntegrator` extensibility point (`ValidationPipelineIntegrator` here, `LoggingPipelineIntegrator` in `.Web`). Reviewed against the Demo (`InvoiceController`, `Requests/Invoices/*`) and README usage.

#### Bugs

- [ ] **`IMediator.SendCommand<TRequest>` param doc is wrong** — `Mediator/IMediator.cs:37` documents `<param name="request">Type of the response.</param>`; it's the request, not "the response" (copy-paste from the response typeparam). Fix the summary.
- [ ] **Validation pipeline throws synchronously instead of returning a faulted task** — `ValidationPipeline<TRequest>` / `<TRequest,TOutput>` (`Pipelines/Validations/…`) call `ThrowIfInvalid(input)` from a non-`async` `HandleAsync`, so the `BusinessRuleValidationException` is thrown on the *calling* thread before a `Task` is returned. When validation is the outermost behavior (no wrapping behavior), a caller that does `var t = SendCommand(...)` then `await t` gets the throw at call time, not await time — violating Task exception semantics. Inside another behavior it's masked because `await next(ct)` re-wraps it. Make `HandleAsync` `async`, or return `Task.FromException`.

#### Design

- [ ] **`IValidatedMessage<TMessage>` forces the request to own its validator and bypasses DI** — `Pipelines/Validations/IValidatedMessage.cs` requires the message to expose `AbstractValidator<TMessage> Validator { get; }`, so the message must construct its own validator (the Demo/tests do `=> new XValidator()` on every access). Validators with dependencies (e.g. a DB uniqueness check) can't be resolved from the container. Prefer resolving `IValidator<TMessage>` from the `IServiceProvider` inside the pipeline (FluentValidation's idiomatic registration) rather than carrying it on the request. Also couples application requests directly to FluentValidation.
- [ ] **Validator property typed as concrete `AbstractValidator<T>` not `IValidator<T>`** — `IValidatedMessage.cs:14` — using the concrete base prevents composed/decorated/wrapped validators. Type it as `IValidator<TMessage>`.
- [ ] **Validation is sync-only** — `ValidationPipeline<TRequest>.ThrowIfInvalid` calls `validator.Validate(...)`; any async rule (`MustAsync`/`CustomAsync`) throws `AsyncValidatorInvokedSynchronouslyException` at runtime. The rest of the codebase already exposes `ValidateAndThrowBusinessAsync`. Add an async validation path (`await validator.ValidateAsync(..., ct)`).
- [ ] **`IMediator` methods lack the `Async` suffix** — `SendQuery`/`SendCommand` return `Task` but aren't `…Async`, unlike `HandleAsync` everywhere else in the codebase. Inconsistent naming convention.
- [ ] **Dispatch is by compile-time `TRequest`, no polymorphic send** — callers must name the concrete request type (`SendCommand<CreateInvoiceDraftCommand, InvoiceId>`); you can't dispatch from an `IRequest<T>`/`ICommand<T>` reference and have the handler resolved by runtime type (MediatR-style `Send(IRequest<T>)`). Reasonable as a deliberate trade-off, but document it — passing a base type silently resolves the wrong (or no) handler.
- [ ] **Three pipeline builders, two ordering mechanisms** — `PipelineBuilder<TInput,TOutput>.Add` appends and `Build()` does `.Reverse()` (`Pipelines/PipelineBuilder.cs:36`); both `ServicePipelineBuilder<>`/`<,>` instead `Insert(0)` in `Add` and **don't** reverse in `Build`. Same net order, but two strategies for one concept is confusing — and `ServicePipelineBuilder<TInput>.Build` names its local `reversedPipelines` (`ServicePipelineBuilder{TInput}.cs:57`) although nothing is reversed (misleading; the `<,>` variant correctly calls it `pipelines`). Pick one mechanism and align the naming.
- [ ] **Builder asymmetry / dead API** — there is an instance-based `PipelineBuilder<TInput,TOutput>` but no `PipelineBuilder<TInput>` for unit commands, and the instance-based builder appears unused (only the `ServicePipelineBuilder` variants are wired through `ServiceMediatorConfig`/integrators). Either complete the symmetry or drop the unused instance builder.
- [ ] **Redundant/inconsistent `abstract` on interface members** — `IServicePipelineIntegrator` marks the `Build…Pipeline` methods `public abstract` but the `Register…Pipeline` methods just `public` (`Integrators/IServicePipelineIntegrator.cs`). Interface methods are implicitly abstract; drop the modifier for consistency.

#### Tests

- [ ] **Integrator path is untested** — `ValidationPipelineIntegrator`, `EmptyPipelineIntegrator`, `MergedPipelineIntegrator`, and the `ServiceMediatorConfig.WithCommand/WithQuery(IServicePipelineIntegrator)` overloads have no coverage. `ServiceCollectionExtensionsTests` only exercises the manual `ServicePipelineBuilder` overloads; the merged Logging+Validation flow shown in the README/Demo is never integration-tested end-to-end through `ServiceMediator`.
- [ ] **No test that a missing handler throws `MediatorException`** — the `?? throw new MediatorException(...)` branches in `ServiceMediator` (all three send methods) are uncovered.
- [ ] **Ordering tests don't pin execution order** — `PipelineTests` record into the call stack *after* awaiting `next` (post-order), so they pass for either inner/outer arrangement; add a pre-`next` ordering assertion to actually guard behavior order.
- [ ] **Cancellation branch untested** — the `IsCancellationRequested` → `Task.FromCanceled` short-circuit in `Pipeline<TInput>`/`Pipeline<TInput,TOutput>` has no test.

#### Minor

- [ ] **Imprecise diagnostics in exception messages** — `ServiceMediator` uses `typeof(TRequest).Name` (ambiguous across namespaces) and `nameof(IQueryHandler<TRequest,TResponse>)` which drops the generic args (renders just `IQueryHandler`). Consider `FullName` / a formatted closed-generic name.
- [ ] **Stray `code-dump/ServiceMediatorConfig.cs`** — a copy of the config lives outside `src/`; remove if it's leftover scratch (repo hygiene).

#### Notes (keep doing)

- Clean marker-interface hierarchy with correct variance: `IRequest<out TResponse>`, `ICommand<out TResponse>`, `in TCommand`/`in TQuery` on handlers.
- `EmptyPipeline<…>` singletons avoid allocation/branching when no behaviors are registered; per-behavior cancellation checks between steps.
- Integrator + `Merge` composition is a genuinely nice, open/closed extension point — `.Web`'s `LoggingPipelineIntegrator` extends the core pipeline story without touching core, and `MergedPipelineIntegrator` flattens nested merges.
- Thorough XML docs, file-scoped namespaces, `nameof` in messages, and DI lifetimes (`Scoped` handlers/pipelines, singleton empty pipeline) are all consistent.

## MartinDrozdik.DDD.Options

Validated configuration options, extracted from `MartinDrozdik.DDD.Web` in `0.9.0` so business and infrastructure layers can use `IOptions<T>` without an ASP.NET Core reference. Contains `IAppOptions`, `IValidatedAppOptions<T>`, `FluentValidateOptions<T>`, `ServiceCollectionExtensions` and `ConfigurationManagerExtensions`; `IWebHostBuilder.SetOption<T>()` stayed in `.Web`. Reviewed file-by-file against the package `README.md`, the Demo (`Options/InvoiceOptions.cs`, `Program.cs:29`) and the `.Web` consumers (`DatabaseOptions`, `StaticFileVersioningOptions`).

### Bugs

- [ ] **`AddAppOptions` does not fail fast on a *missing* section — `required` properties come back `null`** — README:63 promises "Both bind strictly (`ErrorOnUnknownConfiguration = true`) and validate on start, so a typo in a config key is a startup failure rather than a silent default". Strict binding does reject *unknown* keys, but an *absent* section is silent: verified that `AddAppOptions<T>()` for a type with `public required string SomeString { get; init; }` and no configuration at all resolves `IOptions<T>.Value` happily with `SomeString == null`, and `IStartupValidator.Validate()` throws nothing. `required` buys nothing because `OptionsFactory<T>` instantiates through `Activator.CreateInstance`, which bypasses required-member enforcement — and with `<Nullable>enable</Nullable>` that is a `null` sitting in a non-nullable `string`. This is exactly the shape the README's own `SimpleOptions` sample uses (README:54-58), and `InvoiceOptions`/`DatabaseOptions` only escape it because they go through `AddValidatedAppOptions`. Fix: have `AddAppOptions` also assert the section exists (a `.Validate(...)` that the bound section has children, evaluated under `ValidateOnStart`), or drop `required` from the docs and point everyone at `AddValidatedAppOptions`.
- [ ] **`GetOptions`/`GetRequiredOptions` are missing the `class` constraint — "required" silently returns `default` for a struct** — `ConfigurationManagerExtensions.cs:18,33` constrain only `where TOptions : IAppOptions`, unlike `AddAppOptions` (`class, IAppOptions`) and both validated variants (`class, IValidatedAppOptions<T>`). For a `struct` options type `TOptions?` collapses to `TOptions`, so the `options is null` guard at line 37 is dead code. Verified: with the section absent, **both** `GetOptions<TStruct>()` and `GetRequiredOptions<TStruct>()` returned an all-default struct without throwing — the "Throws an exception if the options cannot be bound" contract on line 27 is unenforceable. Fix: add `class` to both, matching the rest of the package.
- [ ] **Registration is not idempotent** — `ServiceCollectionExtensions.cs:51-55`: `AddSingleton<IValidateOptions<TOptions>>` is additive, and so are `BindConfiguration`/`ValidateDataAnnotations`/`ValidateOnStart` in `AddAppOptions`. Verified: calling `AddValidatedAppOptions<T>()` twice yields **4** `IValidateOptions<T>` registrations (2 fluent + 2 data-annotation) and an `OptionsValidationException` that repeats every failure twice. Realistic trigger: a library module registers its own options and the composing app registers them again, or `AddAppServices()` plus a manual call. Fix: `services.TryAddEnumerable(ServiceDescriptor.Singleton<IValidateOptions<TOptions>, FluentValidateOptions<TOptions>>())`, and short-circuit the binding on a marker registration.

### Design

- [ ] **Extensions are bound to `IConfigurationManager`, not `IConfiguration`** — all four helpers (`ConfigurationManagerExtensions.cs:17,32,54,78`) take `IConfigurationManager` although the bodies use nothing beyond `GetSection`, i.e. plain `IConfiguration`. `IConfigurationManager` is implemented only by `ConfigurationManager`, so a library helper, a test, an `IConfigurationRoot`, a bound sub-section, or `ConfigureAppConfiguration` cannot call them at all. The package's own tests show the cost: `ConfigurationManagerExtensionsTests.BuildConfiguration:138` has to spin up a `ConfigurationManager` while `ServiceCollectionExtensionsTests.BuildProvider:126` uses a plain `ConfigurationBuilder`. Widen the receiver to `IConfiguration` (source-compatible for every existing caller) and rename the file/class accordingly.
- [ ] **`FluentValidateOptions` ignores the `name` parameter — named options are validated against an instance that was never bound** — `FluentValidateOptions.cs:14` validates unconditionally, but `BindConfiguration` (`ServiceCollectionExtensions.cs:28`) configures only the default, unnamed instance. Verified: `IOptionsMonitor<T>.Get("SomeOtherName")` throws `OptionsValidationException` reporting the unbound property as empty, which is a confusing way to say "named options aren't a thing here". The framework convention (`ValidateOptions<T>` in `Microsoft.Extensions.Options`) is to carry the name and return `ValidateOptionsResult.Skip` on a mismatch. Either follow it, or document that the section-per-type convention makes named options unsupported by design.
- [ ] **Validated-options `Validator` typed as concrete `AbstractValidator<T>`** — `IValidatedAppOptions.cs:15` exposes `AbstractValidator<T>` rather than `IValidator<T>`, preventing composed/decorated validators. Moved here with the package; same finding as the Mediator `IValidatedMessage` one — worth fixing consistently.
- [ ] **The validator is `static abstract`, so a rule can never take a dependency** — `IValidatedAppOptions.cs:15` is read statically in both consumers (`FluentValidateOptions.cs:19`, `ConfigurationManagerExtensions.cs:63`), never from the container. That is deliberate and load-bearing: `GetRequiredValidatedOptions` runs during startup *before* a provider exists, which is the whole point of `ConfigurationManagerExtensions`. But it means a rule that needs `TimeProvider`, an `IFileSystem` path probe, or any injected service is inexpressible, and it is the same coupling flagged on the Mediator's `IValidatedMessage`. Keep the static path for the startup case, but consider letting `AddValidatedAppOptions<T>` prefer a container-resolved `IValidator<T>` when one is registered, and document the trade-off either way.
- [ ] **Validation failure messages are culture-dependent** — observed during review: a failed options validation rendered as `Failed options validation for ValidatedOptions.SomeString NotEmptyValidator: Pole 'Some String' nesmí být prázdné.` — Czech, because FluentValidation's built-in messages resolve through `ValidatorOptions.Global.LanguageManager` against the ambient culture. A startup failure therefore comes out in whatever locale the container happens to run under, while every other message in the library is English. The core chapter already records that resx localization was removed library-wide for exactly this reason; FluentValidation reintroduces it through the back door. The package cannot fix this unilaterally (`ValidatorOptions.Global.LanguageManager.Enabled = false` is global mutable state), so the call is: document it, or expose an opt-in switch on `AddValidatedAppOptions`.

### Dependency issues

- [ ] **The whole core package is pulled in for two extension methods** — `MartinDrozdik.DDD.Options.csproj:40` references `MartinDrozdik.DDD` solely for `ValidateAndThrowBusiness` (`ConfigurationManagerExtensions.cs:64`) and `TryGetError` + `Error.Details` (`FluentValidateOptions.cs:23-28`), both from `Extensions/ValidationExtensions.cs`. That drags the entire DDD surface (entities, identities, mediator, enumerations, specifications) into a consumer that only wants validated `IOptions<T>` — the same argument that justified extracting this package out of `.Web` in the first place, one level down. Not free to undo: `GetValidatedOptions` throwing `BusinessRuleValidationException` is a core type and part of the public contract, so shedding the reference means changing that contract. Decide explicitly: inline the two conversions and own an exception type, or keep it and state in the README that `.Options` is a DDD-suite package rather than a standalone options library.

### NuGet split

- [x] **Options module could not be used outside a web app** — `IAppOptions`/`IValidatedAppOptions<T>` lived in `MartinDrozdik.DDD.Web.Options`, so a business layer wanting `IOptions<T>` had to reference the whole ASP.NET Core + EF Core + OpenTelemetry stack. **Fixed:** extracted to `MartinDrozdik.DDD.Options`, which depends only on core, FluentValidation and the `Microsoft.Extensions.{Options,Configuration}` packages. Guarded by `MartinDrozdik.DDD.Options.Tests`, which deliberately references no web or hosting package.

### Minor

- [ ] **README calls `AddAppOptions` the "without validation" path, but DataAnnotations still run** — README:51 says "For simpler options without validation", while `ServiceCollectionExtensions.cs:29` calls `ValidateDataAnnotations()`. Verified: a `[Required]` property with a missing section throws `OptionsValidationException` from `IStartupValidator.Validate()`. The method's own doc (line 13, "ensures validation") is equally vague about *which* validation. Say "without FluentValidation — DataAnnotations attributes still apply".
- [ ] **Undocumented failure modes on the `ConfigurationManager` helpers** — none of the four methods carry `<exception>` tags: `GetRequiredOptions`/`GetRequiredValidatedOptions` throw `InvalidOperationException` (lines 39, 85) and `GetValidatedOptions`/`GetRequiredValidatedOptions` throw `BusinessRuleValidationException` from core via `ValidateAndThrowBusiness` (line 64). A caller reading the XML docs cannot tell what to catch — and the core exception type crossing this API is the thing worth advertising most.
- [ ] **`IAppOptions.Section` example doesn't match the convention the repo actually uses** — `IAppOptions.cs:11` says `<example>Application:Database.</example>`, while every options type in the solution uses the `App:` prefix (`DatabaseOptions.cs:12`, `InvoiceOptions.cs:8`, `StaticFileVersioningOptions`). Also nothing rejects an empty `Section`; `BindConfiguration("")` silently binds the configuration root.
- [ ] **Hardcoded absolute paths in the test csproj** — `MartinDrozdik.DDD.Options.Tests.csproj:42,46` reference `S:\_Projekty\domain-driven-design\src\MartinDrozdik.DDD.Tests\.editorconfig`. Machine-specific; it survives only because `Remove`/`None` items tolerate a missing path, so on any other checkout the intent (share the `.Tests` editorconfig) silently does not happen. Repo-wide — all four test projects carry the same two lines — so fix in one pass with `$(MSBuildThisFileDirectory)..\` relative paths, or delete them since `src/.editorconfig` plus the local `.editorconfig` already cover it.

### Tests
